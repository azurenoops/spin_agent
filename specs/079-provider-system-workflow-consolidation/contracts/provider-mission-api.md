# API compatibility and authorization

Reuse existing endpoints/services; route names below are inspected existing
surfaces, not a claim that all requested UI operations are already supported.
See [research](../research.md) for the trace and gaps.

| Existing surface | Reuse/extension boundary |
|---|---|
| `/api/csp/offerings` and offering authorization/boundary/package-version children | Keep provider store authorization, CSP-admin/non-impersonation checks, revision and idempotency handling. |
| Offering `hosting-scope-revisions` and `hosting-assignments` | Preserve immutable scope and assignment identities; expose task-oriented projections rather than duplicate entities. |
| `/api/dashboard/systems/{systemId}/applicable-provider-capabilities` | Return exact release/context eligibility and explicit gaps; do not include provider-private source contents. |
| `/api/dashboard/systems/{systemId}/provider-capability-adoptions` | Pin release/context/assignment; use canonical responsibility subscription handoff, not auto-confirmation. |
| Existing capability subscription/confirmation endpoints | Keep ISSM/ISSO-scoped responsibility review, stale revision checks and impact fan-out. |
| Provider finding/evidence endpoints | Complete UI and sharing handoff using retained artifacts; upload alone never closes a finding. |
| Dashboard exports/package endpoints | Add purpose/snapshot/provenance and scoped operation checks where missing; test production mapper and middleware. |
| eMASS workflow endpoints | Preserve explicit conflict resolution; add outcome recording only after contract review. |
| ConMon dashboard reads and authorization-domain writes | Reuse the four writes already registered in `DashboardAuthorizationEndpoints`; test production registration and scoped permissions before exposing executable rules. Do not add duplicate routes. |

## Contract rules

Implemented additions:

- Optional reviewed `issuingAuthorityType` on provider decision input:
  `person`, `organization`, or absent. Absence remains a source gap; clients must
  not infer type from issuer name.
- `POST /api/v1/systems/{systemId}/packages/validate?purpose=InitialSubmission`
  and the generation body's `purpose` select explicit initial preparation.
  Omission remains Legacy. UI rejects an explicit-purpose response that does
  not confirm the selected purpose.
- AuthorizedBaselineArchive and ChangeSubmission require
  `RetainedPackageSelection`: baseline package ID/hash, recorded decision ID/
  snapshot hash, and for changes a retained preview ID/hash. Validation accepts
  this body; generation nests it under `retainedContext`.
  `GET /api/v1/systems/{systemId}/packages/context-options` supplies authorized
  source options without manual ID/hash copying. Archive/change operations do
  not manufacture a new authorization or claim eMASS receipt. Validation returns
  `sourceContextHash`; the dialog sends it as `expectedSourceContextHash` during
  generation. This stable source fence differs from the full retained envelope's
  integrity hash, which also includes capture time.
- `GET /api/dashboard/systems/{systemId}/documents/ssp/preview` returns actual
  generated JSON, `contentHash`, `generatedAt`, `sourceGaps`, `isPreview: true`,
  and `sourceState: CurrentWorkingData`. It uses existing system-read
  authorization and no-store caching. It is not an approved package snapshot.
- `POST` to that preview route retains exact generated bytes and returns
  `previewId`/`sourceManifest`. `POST .../exports` with
  `{format:"json",sourcePreviewId}` exports those bytes after schema and current
  evidence-permission checks. Both writes accept scoped `Idempotency-Key`.
- Retained export downloads now enforce equality with the route's system ID.
- Provider evidence sharing publishes only explicit, versioned approved summaries
  for named eligible mission systems. Reads/worker/download revalidate grant and
  hash. Original private artifacts are not exposed.
- Manual `Service` scopes coexist with legacy `Azure` scopes in the existing
  allocation/association/adoption models; no Azure ID is required for SaaS.
- Creating a customer `hosting-assignment` retains its own revision, audit and
  idempotency identity. It does not revise an unchanged offering or invalidate
  existing accepted provider reviews. Service-definition changes still require
  current context review/publication; assignment never grants authorization.
- `POST /api/csp/package-imports/{packageId}/supersede-review` accepts
  `expectedRevision`, `replacementPackageId` and `reason`. Ordinary CSP-admin
  authority, an inactive unpublished original, and a published latest
  same-provider/offering replacement are required. Supersession retires active
  review work without rewriting candidate states or hiding retained canonical
  sources. Historical navigation is read-only and identifies the replacement.
  The separate `/archive` command continues rejecting referenced source material.
- Provider-owned source rules and system-owned monitoring rules remain distinct
  authorizations while sharing condition evaluation and existing scheduling.
- eMASS exchange records retain explicit manual transfer/receipt/import outcomes
  separately from conflict-resolution rationale and AO decisions.

1. Continue existing response envelopes and error conventions. Model unsupported,
   denied, stale, conflict, not-found, and temporarily unavailable distinctly.
2. Server identity supplies actor and scope; do not accept mock personas or body
   tenant IDs as authority. Validate target tenant/system and retained references.
3. Publish/associate/adopt/confirm/export remain separate commands and audit events.
4. Requests carry existing revision fences/idempotency keys. Retry uncertain
   responses by reconciling the original key, not creating a new operation.
5. Re-evaluate revoked membership and evidence permissions on read/download and
   job execution. A previously obtained signed job ID is not authorization.
6. Use additive fields and bounded adapters for Dashboard, Web Chat, VS Code,
   M365, CLI and MCP consumers. Trace actual consumers before removing endpoints.
7. Implement document previews through the same reviewed snapshot/generator used
   for exports; do not build an independent browser document assembler.
8. New endpoint names/DTOs require design review after mapping each mock action to
   current endpoints. No endpoint exists merely because a mock button exists.

## Production-host acceptance

Use the production Program/middleware/DI/route registration with isolated
SQLite and synthetic identities; test SQL Server schema/persistence separately.
Existing tests that manually map handlers are valuable unit/integration evidence
but cannot substitute for full-host policy/RLS/worker/download verification.
Test anonymous, denied, cross-tenant, revoked-role, wrong-system, stale revision,
duplicate request, interrupted worker, and successful recovery paths.
