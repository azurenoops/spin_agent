MO / Org portal product brief

Where a mission creates or imports a system and drives it to a documented package. It can run standalone or attach to a CSP offering and adopt a pinned inheritance release the CSP portal published.

Not a second app — overlay /workspaces/organizations/{tenantId}. Saving a form is not an ATO. Export is not eMASS receipt. Attachment is not accepted inheritance.

StandaloneFull baseline; no cloud offering
CSP-attachedAdopt a pinned release; residual work remains
eMASS importWorking copy; eMASS stays system of record where required
Job to be done. Make the next residual documentation task obvious, reuse what the CSP published where it is valid, and keep package facts honest.

Attach sequence (keep distinct)

1. Subscribe / access (CSP what-if) — not inheritance.
2. Associate system to offering — not inheritance.
3. Adopt pinned release — this is inheritance.
4. Confirm residual duties remain open.
5. Declare use (IL, data, connections) for CSP scope-fit — not an SSP body share.

Pick the offering that matches the authorization you need. FedRAMP Moderate does not cover an IL5 mission. A CMMC contractor still owns 800-171 on their environment.

eMASS import

eMASS remains the DoD system of record where required. This portal is the working layer.

Import package metadata as source-backed records with provenance. Do not fabricate missing authorization metadata. Re-import keeps conflicts explicit. Export/stage is package preparation — not submission receipt, not the AO decision.

An imported “Authorized” status is a recorded external fact, not something this portal issued. Import does not create inheritance. Attach after import still requires adopt + residual confirmation.

Residual package work

After a pinned release is adopted, the MO package is not empty.

Four package facts (never collapse)

1. Preparation / readiness · 2. Export · 3. eMASS submission / receipt · 4. AO decision. A ready form is not 2–4.
